# 1. Flash 驱动重构与性能优化
### 1.1 查表法优化 GetSector() （O(n) → O(1））
原来是通过 if else 来判断某个地址位于哪个扇区。比如：
```C
if((Address < ADDR_FLASH_SECTOR_1) && (Address >= ADDR_FLASH_SECTOR_0))
    sector = FLASH_SECTOR_0;
else if((Address < ADDR_FLASH_SECTOR_2) && (Address >= ADDR_FLASH_SECTOR_1))
    sector = FLASH_SECTOR_1;
// ... 一直到 sector 7
```
这个方法需要一个个进行判断，时间复杂度是O(n)，地址越靠后的扇区，比较次数越多。而使用查表法，先计算，再到表中取对应的值，对应的值就是所在的扇区号，只需要计算一次，时间复杂度是O(1)。
```C
/* Lookup table: index = (Address - FLASH_BASE) / 16KB, returns sector number */
static const uint8_t aSectorLUT[32] = {
    0, 1, 2, 3,           /* 0x00000-0x0FFFF: 4 sectors x 16KB ，扇区0-3 */ 
    4, 4, 4, 4,           /* 0x10000-0x1FFFF: Sector 4, 64KB  ，扇区4 */
    5, 5, 5, 5, 5, 5, 5, 5,  /* 0x20000-0x3FFFF: Sector 5, 128KB  */
    6, 6, 6, 6, 6, 6, 6, 6,  /* 0x40000-0x5FFFF: Sector 6, 128KB */
    7, 7, 7, 7, 7, 7, 7, 7,  /* 0x60000-0x7FFFF: Sector 7, 128KB */
};

static uint32_t GetSector(uint32_t Address)
{
    uint32_t index = (Address - FLASH_BASE) / 0x4000;  // 0x4000 = 16KB

    if (index >= 32)
        return FLASH_SECTOR_7;  // 越界保护

    return (uint32_t)aSectorLUT[index];  // O(1) 查表
}
```

### 1.2 统一返回值语义
在 HAL 规范里，所有操作函数的返回值都应该遵循 **HAL_OK = 0（成功）、HAL_ERROR = 1（失败）** 的统一语义。
如果直接用 0/1 来表示的话，可能不知道具体意思，还得开注释或代码。统一语义便于理解

把uint32_t 改成 HAL_StatusTypeDef。 因为这样**接口契约清晰**。任何开发者看到 `HAL_StatusTypeDef` 就知道它是成功/失败二值语义，看到 `HAL_OK`/`HAL_ERROR` 就知道含义。而 `return 0/1/2` 每次都要翻函数注释才能懂。

### 1.3 添加硬件 CRC32 校验接口
#### 1.3.1 为什么需要 CRC32校验
没有 CRC32 这个接口，后续阶段二、三都做不了
阶段二要搞固件签名验签，阶段三要搞无线 OTA 升级——这两个都得靠 CRC32 来保证数据是完整、没被篡改的。
##### 场景 1：OTA 传输过程中数据损坏，会触发重传
你现在升级固件，是通过 Ymodem 协议一个一个包发过来。假如传输过程中 WiFi 信号干扰，某个字节从 `0xAB` 变成了 `0xAC`：
```
发送端：0x0800C000 处写入 0x12345678
接收端：0x0800C000 处收到了 0x12FF5678  ← 中间被干扰了
```

没有 CRC：你写进去就算完了，启动系统直接跑飞，你都不知道是固件坏了。  
有 CRC：写入前算一次 CRC32，写入后再读出来算一次 CRC32，两个值不一样 → 说明数据坏了 → 触发重传。

##### 场景 2：固件完整性验证

设备启动的时候，用 CRC32 把 Flash 里所有固件数据算一遍，跟打包时写入的 CRC 值比对：
```
出厂时固件 CRC32 = 0xA1B2C3D4
启动时重新计算 CRC32 = 0xA1B2C3D4  ✅ 通过
启动时重新计算 CRC32 = 0xE5F6A7B8  ❌ 固件损坏，进入恢复模式
```

这样就能在设备**跑飞之前**检测到问题，自动进入恢复模式等待重新刷机，而不是让用户看到死机黑屏。

##### 场景 3：分片传输 + 断点续传（阶段三）

OTA 升级时固件切成很多小包发送。每个包带一个 CRC32 校验值，接收方收到后比对：
```
包 1：数据 + CRC32=0x1111 → 校验通过 ✅
包 2：数据 + CRC32=0x2222 → 校验通过 ✅
包 3：数据 + CRC32=0x3333 → 校验失败 ❌ → 只重发包 3
```

没这个机制，任何一个包坏了就得**全部重传**。



#### 1.3.2 为什么用硬件 CRC，不用软件算？
STM32F411 的硬件 CRC 外设是**专门做这件事的电路**：

|方式|计算 1MB 数据|
|---|---|
|软件算 CRC32|~500ms（CPU 全速跑）|
|硬件算 CRC32|~5ms（不占 CPU）|

其实就是一句话：把数据往 `CRC->DR` 寄存器里依次写入，硬件自动算好，最后读出来就是结果。CPU 可以在这期间干别的事。

#### 1.3.2 函数实现
```
/**
  * @brief  Computes CRC32 using hardware CRC peripheral.  使用硬件外设计算CRC32校验值。
  * @param  pData: pointer to 32-bit aligned data buffer  指向待校验数据的指针，数据必须是32位对齐的
  * @param  Length: number of 32-bit words to process  待校验数据的长度，单位为32位字
  * @retval Computed 32-bit CRC value  计算得到的CRC32校验值
  */
 //把"往硬件寄存器里写数据、读出结果"的过程封装成一个函数：FLASH_If_CRC32()
uint32_t FLASH_IF_CRC32(uint32_t* pData, uint32_t Length)
{
  uint32_t i;
  __HAL_RCC_CRC_CLK_ENABLE(); // 使能CRC时钟
  CRC->CR = CRC_CR_RESET; // 重置CRC寄存器

  /* 计算CRC32 校验值 */  
  for (i = 0; i < Length; i++)
  {
    CRC->DR = pData[i];  // 输入数据到CRC寄存器
  }
  return CRC->DR;  // 返回CRC32校验值
}
```

# 2. 固件安全体系搭建
包括固件的版本管理，固件的签名校验
### 2.1 定义 AppHeader_t 结构体

#### 2.1.1版本编码宏
把 "v1.2.3" 这样的字符串版本号，变成一个**整数**，这样比较大小又快又省空间。
帮我们自动做这件事
```c
// 写代码时：
APP_MAKE_VERSION(1, 2, 3)  
// 编译时自动变成：
0x01020003   //好处是直接比整数，一次汇编指令完事。如果用字符串 `"v1.2.3"` 和 `"v1.3.0"` 比较大小，要逐字符比好几轮，且非常麻烦
```

#### 2.1.2头部结构体（Header）
**头部结构体是什么**：把固件的"身份证信息"打包成一个结构体，贴在固件数据的前面（但不一定在连续的地址上）。

魔数就是一个**固定值**，用来判断"这块内存里有没有有效数据"。
你的 Flash 布局是这样的：
```
┌─────────────────┐
│  头部结构体      │  ← 0x08008000，存放固件的"身份证"
│  (120字节)      │
│  魔数 | 版本 |   │
│  CRC | 签名 |大小│
├─────────────────┤
│                 │
│  固件数据        │  ← 0x0800C000，实际的程序代码
│  (几百KB)       │
│                 │
└─────────────────┘
```

**为什么要分开存放（头部和固件不在同一个地址）？**
因为 **0x08008000（Sector 2）是独立的扇区**。
- 更新固件时：擦除 Sector 3~7 → 写入新固件 → **头部不动**
- 更新版本信息时：擦除 Sector 2 → 写入新头部 → **固件不动**
互不干扰。而且 Bootloader 启动时只用读 120 字节就能知道固件信息，不需要把整个固件都读出来。

### 2.2 实现读写接口
加两个函数：
```c
// 读：从 0x08008000 读取头部到内存中的结构体变量
HAL_StatusTypeDef APP_ReadHeader(AppHeader_t *pHeader);
// 写：把内存中的结构体写入 0x08008000（需要先擦除扇区）
HAL_StatusTypeDef APP_WriteHeader(AppHeader_t *pHeader);
```

**APP_ReadHeader() 的实现逻辑**：
```
① 把 pHeader 指针指向 0x08008000（强制类型转换）
② 检查 pHeader->magic == APP_HEADER_MAGIC？不是则返回 HAL_ERROR
③ 检查 pHeader->headerVersion == 1？（当前支持的版本）
④ 返回 HAL_OK
```
为什么要检查 magic？因为 Sector 2 出厂可能是 0xFF 全空，不做判断直接当头部读出来就是垃圾数据。

**APP_WriteHeader() 的实现逻辑**：
```
① 擦除 Sector 2（FLASH_If_Erase_One_Sector(FLASH_SECTOR_2)）
② 逐个 word 写入结构体数据（FLASH_If_Write）
③ 回读验证写入是否正确
④ 返回 HAL_OK / HAL_ERROR
```
擦除说明：Flash 的特性是"只能从 1 写为 0，不能从 0 写为 1"，所以写入前必须整扇区擦除（恢复成全 1）。

### 2.3 启动时显示版本信息
在菜单显示或启动时加一段调用：
```C
AppHeader_t header;
if (APP_ReadHeader(&header) == HAL_OK) {
    printf("Firmware: v%d.%d.%d\r\n",
           APP_GET_MAJOR(header.fwVersion),
           APP_GET_MINOR(header.fwVersion),
           APP_GET_PATCH(header.fwVersion));
    printf("Size: %d bytes, CRC32: 0x%08X\r\n",
           header.fwSize, header.fwCRC32);
} else {
    printf("No valid firmware header found.\r\n");
}
```
用户刷机时不知道当前是什么固件版本，显示出来可以：
1. 确认当前固件版本
2. 决定是否要升级新版本
3. 调试时一眼看出固件对不对

### 2.4 版本管理
一个简单的比对函数，Bootloader 判断"这个新固件能不能升级"：
```c
// 比较当前固件版本和待升级版本
HAL_StatusTypeDef APP_CheckUpgrade(uint32_t currentVersion, uint32_t newVersion)
{
    // 规则：新版本 >= 当前版本才允许升级（禁止回滚）
    if (newVersion >= currentVersion)
        return HAL_OK;
    else
        return HAL_ERROR;
}
```
**为什么需要版本比对：**
- **禁止回滚**：如果设备已经跑了 v2.0，攻击者想刷回 v1.0（可能有已知漏洞），比对逻辑会拒绝。
- **避免误刷**：用户拿错旧固件包刷入，比对逻辑直接拦截。
- **这条规则你可以自己定义的**，比如大版本必须相同（`major` 要一致），或者小版本不能降级。

### 2.5 ECDSA 签验签

```C
HAL_StatusTypeDef FLASH_VerifyFirmware(AppHeader_t *pHeader)
{
    uint32_t calcCRC;

    /* ① 检查魔数 */
    if (pHeader->magic != APP_HEADER_MAGIC)
        return HAL_ERROR;

    /* ② 检查头部版本兼容性 */
    if (pHeader->headerVersion != 1)
        return HAL_ERROR;

    /* ③ CRC32 校验固件完整性 */
    calcCRC = FLASH_IF_CRC32(
        (uint32_t*)(APP_HEADER_ADDRESS + sizeof(AppHeader_t)),
        pHeader->fwSize / 4
    );
    if (calcCRC != pHeader->fwCRC32)
        return HAL_ERROR;

    /* ④ TODO: 签名校验（移植 micro-ecc 后补充） */
    // if (uECC_verify(publicKey, ..., pHeader->signature) == 0)
    //     return HAL_ERROR;

    return HAL_OK;
}
```

### 2.6 Python 签名工具 (非必要)

**CRC32  =  快递包裹上的"重量" —— 如果运输过程中箱子破了漏了东西，重量变了，你知道包裹坏了。
ECDSA 签名 = 快递包裹上的"封条 + 你的公章" —— 别人拆了包裹换了东西再封回去，封条不对，收件人一眼看出被动过手脚。—— 只有你有公章（私钥），别人伪造不了。** 

| 问题                    | 一句话回答                                                                                                       |
| --------------------- | ----------------------------------------------------------------------------------------------------------- |
| **cryptography 是什么？** | Python 的一个密码学工具包(**Python 第三方库**)，让你能一行代码算 ECDSA 签名，不用自己写几千行数学代码。cryptography 是最主流、最安全的第三方密码库，Google、微软都在用。 |
| **签名代码干了什么？**         | 读了你的 firmware.bin，算 CRC32，用私钥签名，然后打包成一个带 120 字节头部的 .bin 文件。                                                 |
| **为什么用 Python？**      | 签名是 PC 端的工作，不是单片机的工作。Python 最短、最快、最容易集成到编译流程。                                                               |
| **为什么转 C 文件？**        | 因为公钥必须烧进 STM32 的 Flash 里，而 STM32 不认识 .pem 格式，只认识 C 语言的数组。转成 C 文件就是为了让 Keil 能编译进去。                           |

### 3.2 OTA协议分片的定义
#### 3.2.1. 分片协议是什么，有什么用
**一句话**：把一个大文件切成小块，一块一块传。

**为什么需要切？**
```
你有一个 200KB 的固件要传给手表

不切 → 一次发 200KB
        中间断一下（手机通知弹窗、手晃了一下）→ 全丢了，重头再来
        你怎么知道传输到一半了？不知道

切成块 → 每块 512 字节，一共 400 块
          第 137 块传失败了 → 只重传这一块
          第 137 块传到一半断电了 → 上电后问"上次传到第几块了？"→ 从那里继续
```
就像寄 200 本书：你不会把它们捆成一个大包裹寄（丢了全完蛋），而是分成 400 个小包裹，每个有编号，丢了哪个补寄哪个。

**协议 = 你和对方约定好的沟通规则**：
```
你说：我要发固件了，总共 400 片
手表：好，发吧
你说：这是第 0 片，512 字节，CRC 是 0xABCD
手表：收到，CRC 校验通过（ACK=0x06）
你说：这是第 1 片...
...
手表：400 片全收到了，整体 CRC 校验通过（OTA_DONE=0x04）
```
没有这套规则，对方就不知道"你在发什么""发完了没""对不对"。


#### 3.2.2. 协议常数是哪里来的？需要查资料吗？

**不需要查资料，这些是你自己定义的。**

**规定好的东西**是 TCP/IP、HTTP、Ymodem——这些是业界的标准协议，你不能自己改。

但你做的是 **私有协议**——只在你自己的手机 APP 和你的手表之间用，**你说多少就是多少**。
```
// 你自己定的规矩：
#define OTA_MAGIC_HEAD      0xAA55  // ← 你选了这个数
#define OTA_MAGIC_TAIL      0x55AA  // ← 你选了它的反码
#define OTA_PACKET_SIZE     512     // ← 你决定每片 512 字节
```

**选这些数有什么讲究？**

| 常量       | 为什么选这个数                      |
| -------- | ---------------------------- |
| `0xAA55` | 常见的小端字节序魔数，不容易跟随机数据撞上        |
| `512`    | UART 缓冲区刚好装得下，大了容易丢，小了协议开销太大 |
| `CRC16`  | 每片只要 2 字节校验，足够检测传输错误         |

你可以选 `0xDEAD`、`0xBEEF`、`1024`、`200`——**只要你手机端和手表端用同一套数就行**。

#### 3.2.3. 响应码 0x06、0x15 是哪里来的？

```
#define OTA_ACK   0x06
#define OTA_NAK   0x15
```

这两个数字**不是你自己发明的**，是 ASCII 控制字符：

| 十六进制   | ASCII 名称                       | 含义             |
| ------ | ------------------------------ | -------------- |
| `0x06` | **ACK** (Acknowledge)          | 确认收到，没问题       |
| `0x15` | **NAK** (Negative Acknowledge) | 没收到，或收到了但不对，重发 |
| `0x04` | **EOT** (End of Transmission)  | 传输结束           |
| `0x18` | **CAN** (Cancel)               | 取消传输           |

**为什么用这些数？**
因为早在 1970 年代的串口协议里，大家就约定好用这些值做确认/否认。今天几乎所有通信协议（Xmodem、Ymodem、Zmodem、甚至一些 BLE 私有协议）都沿用了这套定义。

你完全可以自己定义：
```c
#define OTA_ACK   0x55  // 你也可以用 0x55
#define OTA_NAK   0xAA
```
但用 0x06/0x15/**好处是别人读你代码一眼就能认出这是 ACK/NAK**，不需要猜。


#### 3.2.4. 状态枚举是干什么的
**不用枚举，用数字也行**：
```c
uint8_t state = 0;  // 0=IDLE, 1=WAIT_CONNECT, 2=RECEIVING...
if (state == 1) { ... }  // 这是什么状态？要看注释才知道
```

**用枚举的好处**：
枚举就是给数字起名字，让代码能读懂，不用看注释，名字就是文档。除了可读性，没有其他区别。


#### 3.2.5. OTA 上下文是什么？为什么需要结构体？

> 是不是就是看接收了多少个数据块？
  **对，但不止。**

你要跟踪的信息不止"收了多少个"：
```
OTA 运行期间需要记住的东西：
├── 当前状态（IDLE / RECEIVING / DONE?）
├── 总共有多少片（totalPackets）
├── 已经收了多少片（currentPacket）
├── 当前正在处理的片的数据缓冲（buffer[512]）
├── 收到的总字节数（bytesReceived）
└── 固件预期的 CRC32 值（firmwareCRC32）
```

这些变量如果散落在文件里：
```c
// BLE_OTA.c
static BLE_OTA_State_t state;
static uint16_t totalPackets;
static uint16_t currentPacket;
static uint8_t  buffer[512];
static uint32_t firmwareCRC32;
static uint32_t bytesReceived;
```

也能工作。但用结构体打包在一起：
```c
typedef struct {
    BLE_OTA_State_t state;
    uint16_t totalPackets;
    uint16_t currentPacket;
    uint8_t  buffer[512];
    uint32_t firmwareCRC32;
    uint32_t bytesReceived;
} BLE_OTA_Ctx_t;

static BLE_OTA_Ctx_t otaCtx;  // 整个 OTA 状态就一个变量
```
**好处**：
1. 传递方便——`BLE_OTA_Process(&otaCtx)` 比传 6 个参数简洁
2. 重置方便——`memset(&otaCtx, 0, sizeof(otaCtx))` 一行清零
3. 断点续传时——整个结构体可以一次性写入 EEPROM 保存

**打个比方**：

> 不做饭的人厨房是这样的：盐在左边抽屉、酱油在右边柜子、锅在灶台下——做个饭到处找。
> 
> OTA 上下文 = 一个**调料托盘**，把所有东西放在一个盘子上端过去，清爽又方便找。

#### 3.2.6总结你的问题

|你的问题|一句话答案|
|---|---|
|分片是什么|大文件切小块，失败只重传小块|
|常数要查资料吗|**不用**，你自己定的规则，收发两端一致就行|
|这是 Ymodem 吗|**不是**，这是 BLE OTA 自有协议|
|响应码 0x06 哪来的|**ASCII 标准**的 ACK 字符，沿用 50 年的惯例|
|枚举干什么|给状态起名字，代码可读性更好|
|上下文为什么用结构体|把所有相关变量打包成一个整体，好管理好传递|

```
上电

  │
  └─ 没按 KEY1

      ├─ 读 AppHeader（FLASH_If_Read_APPHeader）
      │   │
      │   ├─ magic 不对？ ──→ ③ 恢复模式  goto recovery_mode;
      │   │
      │   └─ magic 对了 → 验固件 CRC32
      │       │
      │       ├─ CRC 不对？ ──→ ③ 恢复模式  goto recovery_mode;
      │       │
      │       └─ CRC 对了 → 跳转 APP
      │
      ③ 恢复模式：  recovery_mode:
         ├─ LCD 显示 "Firmware damaged. Entering recovery..."
         ├─ KT6328_BLE_Init(OTA_OnDataReceived)
         ├─ BLE_OTA_Start()    → 状态 = OTA_WAIT_CONNECT
         └─ while(1) 里跑 BLE_OTA_Process()
```

### 3.7 Python 发送工具
手表端（BLE_OTA.c）已经写好了**接收逻辑**，但固件得有个**发送方**把它推过去。Python 发送工具就是这个发送方 —— 一个跑在电脑上的 Python 程序，通过 PC 蓝牙连上 KT6328，把固件推给手表。

**一句话总结它做的事：** 
```
读固件 → 切成 512B 帧 → 加头部/CRC → 逐帧发 → 等 ACK/NAK → 收完验证 → 支持断点续传 → 显示进度
```

**发送工具的工作流：** 
```
python ble_ota.py firmware_signed.bin
      │
      ├─ ① 扫描蓝牙，找 "OV-Watch" 设备
      ├─ ② 连接
      ├─ ③ 发"开始"信号 → 手表回 [0~N，或断点值]
      │       └─ 读到断点 X → 从第 X 片开始发
      ├─ ④ 循环：组装第 i 帧 → 发 → 等 ACK?
      │       ├─ ACK → i++，下一帧
      │       ├─ NAK → 重发当前帧
      │       └─ 超时 → 重发/断线重连
      ├─ ⑤ 最后一片发完
      └─ ⑥ 显示 "OTA 完成"
```
