# 01 把APP数据指定存储到0x0800c000后
Core/Src/main.c:71

```C
  //SCB是系统控制块，用于配置系统时钟、中断等（system control block）
  //VTOR是向量表地址，用于指定中断向量表的地址（vector table offset register）
  //中断向量表是一个存储中断处理函数地址的表格，当中断发生时，内核会根据中断号从这个表格里找到对应的中断服务函数，然后跳转到该地址执行
  SCB->VTOR = 0x0800C000U;
```

**只要你告诉编译器中断向量表的位置，其他代码和数据就会自动跟在后面，不需要你手动指定。**
 
这一切都是链接脚本在背后自动处理的，你只需要告诉链接脚本中断向量表的起始地址，它就会自动把所有代码和数据都放到正确的位置。
 
链接脚本会把程序分成几个部分：第一部分是中断向量表，放在最前面，地址由你指定，比如0x0800C000；第二部分是代码段，紧随向量表之后，存放函数体和常量数据；第三部分是数据段，存放在RAM里，存放全局变量和静态变量。这些部分的位置都是链接脚本自动计算的，你只需要指定向量表的起始地址就好了。
 
比如在链接脚本里，你只需要写一句 __Vectors = 0x0800C000; 链接脚本就会自动把中断向量表放到0x0800C000的位置，然后把代码段放到向量表结束之后的位置，完全不需要你手动计算地址。
 
这是因为应用程序的所有代码和数据在编译的时候就已经被链接脚本放到了正确的位置，它们的地址都是相对于向量表起始地址的偏移量。你只需要告诉内核向量表的新位置，内核就能找到所有的中断服务函数，应用程序也能正确访问自己的代码和数据。
 
最终的内存布局就是这样的：Bootloader在最前面，然后是升级标志区，接着是APP的向量表，最后是APP的代码和数据。所有这些都是链接脚本自动处理的，你只需要指定向量表的起始地址就好了。关于链接脚本和内存布局。

# 02 用RTC唤醒定时器
User/Tasks/Src/user_HardwareInitTask.c:46

```C
	//设置RTC唤醒定时器，周期为2秒，使用RTC时钟源
    if(HAL_RTCEx_SetWakeUpTimer_IT(&hrtc, 2000, RTC_WAKEUPCLOCK_RTCCLK_DIV16) != HAL_OK)
    {
      Error_Handler();  //错误处理函数
    }
```

这个设计其实挺巧妙的，**这是一种硬件初始化的健康检查机制** ，我给你好好分析一下。
 
首先这个**最高优先级的硬件初始化任务，它的职责就是把所有硬件都初始化好，然后再启动其他任务。** 但如果某个硬件初始化失败了，比如传感器挂了或者外设没响应，就很可能导致任务卡住，整个系统就僵住了。
 
**那为什么要用RTC来做这个检查呢？** 
1. 因为RTC是独立运行的，它有自己的时钟源，即使系统其他部分卡住了，RTC仍然会继续计时。
2. 而且RTC唤醒是硬件中断，不受任务调度影响，可以强制唤醒系统，这样就能在系统卡住的时候及时发现问题。
3. RTC功耗低，适合长时间的超时检测
 
**为什么是两秒呢？** 
这是一个比较合理的折中时间。既不会因为太短导致误触发，比如初始化稍微慢一点就被当成错误处理；也不会因为太长让系统卡住太久才被发现。一般硬件初始化都能在几百毫秒内完成，两秒足够应对绝大多数情况了。
 
**具体流程是这样的：** 
启动硬件初始化任务的同时，设置RTC两秒后唤醒。如果一切正常，初始化完成后会取消RTC唤醒，然后启动其他任务。但如果初始化卡住了，比如某个外设没响应导致任务死等，RTC两秒后就会触发唤醒中断，系统就会跳转到错误处理函数，进行复位或者其他补救措施。
 
这样设计的好处就是可以避免系统卡在初始化阶段，提高系统的可靠性。特别是在工业控制或者无人值守的场景下，这种机制可以让系统在出现问题时自动恢复，不需要人工干预。

## hw_interface.power.init()
**hw_interface:** 全局结构体变量，包含了所有硬件接口（如蓝牙，电源，LCD等）
**power：** 子结构体，专门负责电源管理相关接口
**init:** 函数指针，指向真正的电源初始化函数
#### 多层调用流程
 ```C
//1. 业务层调用
hw_interface.power.init();
//2. 接口层判断    条件编译
#if HW_USE_BAT
	power_init()

 ```
#### 每一层的职责:
**业务层:** 只关心"做什么"，不关心"怎么做"
**接口层:** 提供统一接口，处理功能开关和参数配置
**初始化层:** 协调多个硬件模块的初始化顺序
**底层驱动:** 直接操作硬件寄存器，完成具体功能
 
#### 这种设计的优势
🧩 **模块化设计：** 每一层都可以独立修改和替换
🔄 **可扩展性强：** 新增功能只需要添加对应的接口和实现
🖊️ **便于测试：** 可以单独测试每一层的功能
👥 **团队协作：** 不同的人可以负责不同的层，并行开发

## 条件编译
**什么是条件编译？** 
条件编译是C语言的一种预处理指令，通过#if、#else、#endif等指令，让编译器根据不同的条件编译不同的代码段。
 
**为什么要用条件编译？** 
**代码复用：** 同一个代码库支持多个硬件版本，不用维护多套代码
**功能开关：** 方便启用或禁用某些功能，快速切换不同配置
**跨平台兼容：** 同一个代码可以在不同编译器和操作系统上编译
**调试方便：** 可以轻松开启或关闭调试信息，不用删除调试代码
 
**常见用法** 
```C
// 1. 硬件版本选择
#define HW_VERSION_V1 1
#define HW_VERSION_V2 0

#if HW_VERSION_V1
v1_hardware_init();   // V1版本硬件初始化代码
#elif HW_VERSION_V2
v2_hardware_init();   // V2版本硬件初始化代码
#else
default_hardware_init();   // 默认版本硬件初始化代码
#endif

// 2. 调试信息开关
#define DEBUG 1

#if DEBUG
printf("调试信息: 初始化完成\n");
#endif
```

**它是怎么工作的？**  
条件编译是在预处理阶段处理的，编译器会根据宏定义的值决定哪些代码段要保留，哪些要删除。被删除的代码不会被编译，也不会出现在最终的固件里。
 
**嵌入式开发中的特殊用法** 
1. 芯片型号选择：同一个代码支持STM32F103和STM32F407等不同芯片
2. 外设配置：启用或禁用某些外设，比如蓝牙、WiFi、LCD等
3. 地区适配：不同地区的法规和标准不同，配置不同的参数
4. 功耗配置：选择不同的功耗模式，比如高性能模式或低功耗模式
 
**最佳实践** 
1. 把所有宏定义集中放在一个配置头文件里，方便管理
2. 给宏定义加上默认值，避免未定义导致编译错误
3. 使用有意义的宏定义名称，提高代码可读性
4. 不要滥用条件编译，过多的条件编译会降低代码可读性

# 05 低功耗模式
user/Tasks/user_RunModeTasks.c

1. **STM32 STOP模式**：STOP模式是STM32最低功耗的运行模式（仅主调供电，CPU停止，所有外设时钟关闭），通过外部中断（RTC、按键、触摸、UART）唤醒。
2. **FreeRTOS任务同步**：用消息队列实现任务间通信，避免全局变量的竞争，是嵌入式RTOS的标准用法。
3. **低功耗状态机**：用「标记变量 + 阈值判断」实现低功耗状态流转，避免重复触发，同时兼顾用户体验。
4. **硬件直接操作**：直接操作 `SysTick->CTRL` 寄存器实现SysTick的开关，这是嵌入式开发的核心能力（理解硬件寄存器的作用）。
5. **防误唤醒机制**：通过「抬手检测+唤醒源判断」过滤无效唤醒，避免频繁唤醒导致功耗增加。

#### 整体逻辑：
1. 用户设置「10秒变暗、30秒休眠」→ 无操作10秒 → 屏幕变暗 → 无操作20秒 → 系统进入STOP模式
2. 用户按按键/点击屏幕 → 触发空闲打断 → 亮度恢复，重新计时
3. 用户抬手（开启抬手亮屏）→ MPU检测到姿态变化 → 触发STOP模式唤醒 → 恢复显示
4. 无效唤醒（比如误碰触摸）→ 自动重新进入STOP模式，降低功耗
