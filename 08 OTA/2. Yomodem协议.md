Ymodem 是一种在嵌入式领域应用极广的**串行文件传输协议**，是一套用于串口通信的“可靠文件快递规则”。它由 Chuck Forsberg 在 1980 年代初期基于 Xmodem 改进而来，**核心目标是解决大文件传输效率低和无法批量传输的问题。在固件升级场景中，它常与 IAP 机制配合，负责将固件文件通过串口（有线）或蓝牙（无线转串口）可靠地“搬运”到设备端

---
# 1. 核心特性：它为什么被广泛使用？
Ymodem 的流行，源于它在效率和可靠性之间取得了很好的平衡。

| 特性                      | 说明                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------- |
| **双数据块模式**              | 支持 **128 字节**（SOH 帧）和 **1024 字节**（STX 帧）两种数据块。日常使用通常指 Ymodem-1K，即优先使用 1024 字节块，传输效率显著高于 Xmodem 的 128 字节。 |
| **文件信息预传输**             | 在发送数据前，会先发送一个**起始帧**，里面包含**文件名**和**文件大小**。接收方（如 Bootloader）可以提前知晓固件信息，便于检查存储空间是否足够。                      |
| **批处理能力**               | 支持在一次会话中连续发送多个文件，这是它相对于 Xmodem 的重要改进。                                                                    |
| **CRC-16 校验**           | 每个数据块都附带 CRC-16 校验码，用于检测传输过程中是否出现位错误。                                                                    |
| **停等（Stop-and-Wait）机制** | 发送方每发完一个数据块，必须等待接收方的确认（ACK）后，才会发送下一个数据块。这保证了传输的有序和可靠，但也限制了速度。                                            |

---
# 2. 帧结构：数据是如何打包的？
Ymodem 的每一“包”数据都有固定的结构，主要分为三种帧类型。

**1. 起始帧（文件信息帧，133 字节）**  
**它不包含固件数据，只承载文件元数据。**
- **帧头**：`SOH` (0x01)，表示这是 128 字节的数据包
- **块编号**：固定为 `0x00`，表示这是起始帧
- **块编号反码**：固定为 `0xFF`，是快编号的反码，用于校验块编号是否正确。
- **数据区**：依次存放 **文件名**（以 `0x00` 结尾）、**文件大小**（以 ASCII 字符串表示，如 “135168”，以 `0x00` 结尾），剩余空间用 `0x00` 填充至 128 字节。文件名和文件大小之间用空格分隔，比如：“firmware.bin 102400”
- **帧尾**：2 字节的 CRC-16 校验码。

**2. 数据帧（1029 或 133 字节）**  
**用于传输实际的文件内容。** 
- **帧头**：`STX` (0x02) 表示 1024 字节数据；`SOH` (0x01) 表示 128 字节数据。
- **块编号**：从 `0x01` 开始递增，每发送一个数据包就加1，到 `0xFF` 后回到 `0x00`。
- **块编号反码**：块编号的按位取反值。
- **数据区**：128字节或1024字节的文件数据。若数据不足128或1024字节，则用 `0x1A` (SUB) 填充
- **帧尾**：CRC-16 校验码。用于校验整个帧的正确性

**3. 结束帧（133 字节）**  
标志传输结束。
- **帧头**：`SOH` (0x01)。
- **块编号**：固定为 `0x00`
- **块编号反码**：固定为 `0xFF`
- **数据区**：用128 字节的 `0x00` 填充。
- **帧尾**：CRC-16 校验码

# 3. 控制字符：通信的“指令”
除了数据帧，Ymodem 还使用一系列单字节控制字符进行握手和错误处理。

| 字符        | ASCII 码 | 功能                                      |
| --------- | ------- | --------------------------------------- |
| **`C`**   | 0x43    | 接收方发出的**启动请求**，表示准备就绪，请用 CRC16 校验模式传输文件 |
| **`ACK`** | 0x06    | **确认**，表示数据块接收正确。请求发送下一个数据块             |
| **`NAK`** | 0x15    | **否认**，表示数据块校验失败或超时，请求重新发送当前数据块         |
| **`EOT`** | 0x04    | **传输结束**，发送方告知数据已全部发完。                  |
| **`SOH`** | 0x01    | 128 字节数据块的起始标志。                         |
| **`STX`** | 0x02    | 1024 字节数据块的起始标志。                        |
| **`CAN`** | 0x18    | **取消**，连续发送两个 `CAN` 可中止传输。              |

---
# 4. 完整传输流程：
1. **握手阶段：** 接收方（设备端 Bootloader）进入接收模式，**循环发送字符 `C`**，等待发送方（PC 上位机）响应。
   
2. **发送文件头：** 发送方收到C字符后，发送**起始帧** SOH +00 +FF +文件名 +文件大小 +CCR 16
   
3. **确认文件头：** 接收方校验起始帧。若正确，则**发送 `ACK`**，并**紧接着再发送一个 `C`**，表示准备好接收第一个数据块。如果校验失败，则回送 `NAK` 请求重传起始帧。
   
4. **发送数据：** 发送方收到 `C` 后，开始发送**数据帧**（STX +块编码 +块编码反码 +1024字节数据 +CRC16），块编号从 `0x01` 开始。
   
5. **接收数据：** 接收方每收到一个数据块，就进行 CRC 校验。
    - **校验成功**：回复 `ACK`，发送方继续发送下一块。
    - **校验失败或超时**：回复 `NAK`，发送方**重传当前数据块**。同时，接收方会持续发送 `C` 来请求下一块，以防发送方未收到 `ACK`。

6. **结束传输：** 发送方发送EOT，接收方发送NAK，发送方再发送EOT，接收方再发送ACK，发送方发送结束帧，接收方发送ACK
	- 发送方发送一个 `EOT` 字符。
	- 接收方收到 `EOT` 后，为了确保不是误码，**首次会回复 `NAK`**。发送方再次发送 `EOT`，接收方确认后回复 `ACK`。
	- 发送方发送一个**全零的结束帧**（块编号为 0，数据区全 0x00）。
	- 接收方校验结束帧后回复 `ACK`。至此，单次文件传输完成。

----
# 5. 注意事项
- **超时重传**：每个阶段都要设置超时时间（一般为3秒），如果超过3秒还没有收到响应，就需要重新发送请求或数据。
- **重发次数限制：** 需要设置最大重发次数（一般为3次），如果重发超过三次仍然失败，就需要终止传输
- **缓冲区大小：** 接收缓冲区大小需要至少容纳一个完整的1024字节的数据帧，加上帧头和校验码，一般建议设置为1030字节以上
