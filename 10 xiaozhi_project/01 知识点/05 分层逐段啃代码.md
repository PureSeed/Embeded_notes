# 1. main
## 1.1 main.cc
##### 整体启动流程
```
芯片上电
  → FreeRTOS 内核启动
    → app_main()（本文件）
      ① esp_event_loop_create_default()    // 事件总线就绪
      ② nvs_flash_init()                    // 持久化存储就绪
      ③ Application::GetInstance().Start()  // 应用启动
            → 初始化硬件板子
            → 连接WiFi/4G网络
            → 建立WebSocket/MQTT到服务器
            → 开始音频处理管线（麦克风→编码→发送 / 接收→解码→扬声器）
```

**代码解析：**
```C++
auto& app = Application::GetInstance();  // 拿到那个唯一的"应用管理器"对象
app.Start();                             // 让它开始运转（初始化硬件、连接网络、开始语音交互）
```
**为什么要用单例？** 因为整个设备只需要一个"应用管理器"，它管理着音频服务、协议、显示、状态等所有全局资源。如果允许多个实例，会导致资源冲突（比如两个对象抢麦克风）。所以用私有构造 + 静态实例来强制"全局唯一"。
```
app.Start()
  ├── 创建事件组 event_group_（用 MAIN_EVENT_SCHEDULE、MAIN_EVENT_SEND_AUDIO 等标志）
  │     └── application.h 顶部宏：
  │         MAIN_EVENT_SCHEDULE        (1 << 0)   // 调度任务
  │         MAIN_EVENT_SEND_AUDIO      (1 << 1)   // 发送音频
  │         MAIN_EVENT_WAKE_WORD_DETECTED (1 << 2) // 唤醒词检测
  │         MAIN_EVENT_VAD_CHANGE      (1 << 3)   // VAD语音活动变化
  │         ...
  ├── 初始化硬件板子（通过 Board::GetInstance()）
  ├── 初始化 AudioService 音频服务
  ├── 创建定时器（clock_timer_handle_）
  ├── 创建 MainEventLoop 主事件循环任务
  └── 连接服务器，开始运行
```

## 1.2 application.h

### 1.2.1 两个架构约定
#### 一、 Schedule(lambda)：
- 把 lambda 投递到主循环队列，由主线程串行执行 → 解决多线程竞争。把"要执行的代码块"当成消息，扔进队列，主线程串行取出执行。**它底层就是一个队列 + 一个消费它的线程/任务**

- Schedule 解决的不是"共享资源改得安不安全"，而是"只让一个线程改，从根上不需要考虑安不安全"。所以只需要在任务放到队列上的时候加锁就可以了
  打个比方：**不是教四个人"轮流用笔记本"，而是干脆只让一个人管笔记本，其他三个人有事写纸条**
  所有状态变更串行化到 `main_event_loop` 线程，**没有一把锁争夺**。锁只用在 `Schedule` 的队列本身。
  锁保护的是"往队列里塞"这个动作（数据结构安全）。业务状态之所以不需要锁，是因为"改业务状态的代码"被强制限制在主循环单线程里跑——这是"用架构隔离"替代"用锁保护"。

- 多个线程 ──塞任务──► [ 队列 ] ── 一个线程（主循环线程main_loop）挨个取出──► 逐个执行。只用在把任务放到队列上去的时候，需要锁。任务到队列的时候，会有事件组标志位提醒，唤醒线程，这样就避免了线程一直轮询浪费CPU资源的问题。

- 没有优先级的概念，所以一般紧急任务为了避免被别的任务堵住，所以一般紧急任务都不会放到schedule中，一般会用事件组的其他bit（标志位）来提醒。 Schedule 队列内部无优先级；但整个主循环通过"if 分支的顺序"实现了"事件级优先级"——紧急 bit 排前面，SCHEDULE 排中间，CLOCK 排最后。紧急任务不走 Schedule，不只是因为"队列没优先级"，更因为它需要"越过还在排队的任务，立刻被执行"——而这个能力只能靠"独立的 bit + if 排前面"来实现。

- schedule中一般放业务动作，共同点：都是"动作"，都有"上下文"（对象、字符串、数据包），都不能用固定 struct 表达。这些动作都是"允许排队等待"。这些动作的共性：**晚几毫秒做也可以，但不能乱序做、不能并行做**。这些恰恰是"排队串行"最适合的任务类型。

- 事件主循环本身也是一个任务，一般是中低优先级，MainEventLoop 里执行的不全都是来自 Schedule投递的任务。有些事直接在循环里用 if 分支处理（bit 触发），有些事从 Schedule 队列取出处理（队列触发）。
- 

**所以"搞 Schedule"的本质 = 用 C++ 语言特性，在 FreeRTOS 事件组之上，造一个"能装任意动作"的队列。** 不是"放弃 FreeRTOS"，是"从 FreeRTOS 提供的积木里挑一块，再包上一层 C++ 皮"。

**并没有放弃 FreeRTOS 队列，只是把"队列里装什么"换了一种类型**：
**传统的队列：**
- 队里装的是**数据 + 类型标签** 
- 消费者必须**再有一个 dispatch switch** 根据类型做事
- **每新增一种操作，要改两处**：枚举 + switch
- **payload 大小固定**（没法装 `std::string` 这种变长数据）
- 消息 = "发生了什么"
**schedule：**
- 队里装的是**函数对象（闭包）**，包含代码 + 捕获的数据 
- **消费者完全不需要 dispatch**——它不知道自己在执行什么
- **新增操作零成本**——直接写一个新 lambda 投进去
- **payload 大小无限制**（捕获 `std::string`、`std::shared_ptr` 都行）
- 消息 = "该做什么"

|       | FreeRTOS Queue（数据）    | `Schedule`（闭包）          |
| ----- | --------------------- | ----------------------- |
| 队列里装的 | 结构体/字节                | `std::function<void()>` |
| 消息的语义 | "发生了什么"               | "要做什么"                  |
| 消费者   | 需 dispatch switch     | 直接调                     |
| 新增消息  | 改枚举 + 改 switch        | 写个新 lambda              |
| 数据大小  | 创建时固定                 | 动态                      |
| 拷贝成本  | memcpy                | move（近乎零拷贝）             |
| 内存管理  | 栈上 struct             | 堆 + SBO                 |
| 阻塞等待  | xQueueReceive         | EventGroup WaitBits     |
| 多路复用  | QueueSets（麻烦）         | EventGroup（天然支持）        |
| 上下文   | 可在 ISR 用 `...FromISR` | **不能在 ISR 用**（mutex 限制） |
| 适用场景  | 数据流（传感器读数、音频帧）        | 命令流（状态机、UI 操作）          |
**为什么要用schedule，：** 
- 加锁从"到处都是"变成"只在 push_back 那一瞬间"
- 业务逻辑从"分散在回调里"变成"集中在 MainEventLoop 里串行执行"
- 状态机从"处处判断并加锁"变成"单线程访问，天然无锁"

**为什么不能用 FreeRTOS Queue 直接装 lambda：** 
- FreeRTOS Queue 底层是 `memcpy` 复制固定大小的内存块
- `std::function` 内部可能包含堆分配的闭包对象（捕获了 `std::string` 等）
- **`memcpy` 复制 `std::function` 是未定义行为**——它会复制内部的指针，导致两次析构同一块堆内存（double free）
- 所以 FreeRTOS Queue 天生不适合装 `std::function`——必须用 C++ 的容器（`std::list` / `std::queue`）

**这个架构必须要遵循的铁律：** 
铁律 1：所有状态修改必须通过 `Schedule`
铁律 2：lambda 捕获必须**自包含**，本质是lambda 被投递后，必须"独立于所有外部资源的生命周期"——因为它未来会在任意时刻、在另一个线程被执行，此时外部资源可能早就没了。因为 `OnIncomingJson` 回调返回后，cJSON 的整个树（`root`）就被 `cJSON_Delete` 了。你捕获的 `text->valuestring` 指向的那块内存已经 free。等到主循环执行这个 lambda 时，就是访问已释放内存。
铁律 3：`Schedule` 里不做阻塞等待，

```
┌──────────────────────────────────────────────────────────────┐
│  Schedule 速查卡                                              │
├──────────────────────────────────────────────────────────────┤
│  本质：队列 + 一个消费线程。装的是"动作"（lambda），不是"数据"  │
│  目的：单线程串行改状态，用"架构隔离"替代"到处加锁"            │
│  锁：  只保护 push_back（链表结构），不保护业务状态            │
│  唤醒：塞完任务按事件组的一个 bit（门铃），避免轮询            │
│  执行：主循环 move 整条链表出来 → 锁外执行，互不干扰          │
│                                                              │
│  分工：                                                       │
│    · 紧急/高频/固定逻辑 → 事件组 bit（直接 if 处理）           │
│    · 业务动作/带上下文/允许排队 → Schedule（闭包任务）        │
│                                                              │
│  优先级：Schedule 队列内部无优先级（FIFO）                     │
│          但主循环 if 的书写顺序 = 事实上的"事件级优先级"          │
│          紧急 bit 写前面，SCHEDULE 写中间，CLOCK 写最后         │
│                                                              │
│  为什么不直接用 FreeRTOS Queue？                               │
│    · FreeRTOS Queue 用 memcpy 复制固定块                      │
│    · std::function 内含堆对象，memcpy 会 double free           │
│    · 所以必须用 C++ 容器（std::list）自己管理                    │
│                                                              │
│  三条铁律：                                                   │
│    1. 所有状态修改走 Schedule（保证单线程）                      │
│    2. lambda 捕获必须自包含（深拷贝，不捕获裸指针）               │
│    3. Schedule 内不做阻塞等待（不卡主循环）                      │
└──────────────────────────────────────────────────────────────┘
```


#### 二、 一些其他问题

```
外部线程/Schedule 调 SetBits  →  事件组被置位  →  WaitBits 返回  →  主循环的 if(bit&) 分派
     ↓                              ↓                  ↓                     ↓
   唤醒动作                    唤醒信号             被唤醒             处理已醒的 bit
```
整个系统里"唤醒任务"的机制只有一种：事件组。Schedule "给主循环塞任务"；`if(bit&)` 不负责唤醒，它只是"主循环醒了之后怎么分派"。真正的"叫醒"动作，永远是别人调 `xEventGroupSetBits`，主循环从 `xEventGroupWaitBits` 返回。
"三个机制"实际上只有一个唤醒机制（事件组）+ 两种"投递方式"（直接投 bit / 通过 Schedule 投闭包再投 SCHEDULE bit）

| 名字             | 性质                  | 用在哪里                    | 为什么                  |
| -------------- | ------------------- | ----------------------- | -------------------- |
| **事件组**        | **唤醒信号总线**          | 外部线程通知主循环"该干活了"         | 支持多路等待、原子、便宜、不会丢     |
| **Schedule**   | **带 payload 的投递方式** | 业务动作（携带数据、需保序、允许排队）     | 装 lambda，不用 dispatch |
| **`if(bit&)`** | **主循环里的分派代码**       | 主循环醒了之后"哪个 bit 置了就做对应事" | 决定处理顺序（这就是"事件优先级"）   |
```
外部线程要做某事
   │
   ├─ 事情= 纯信号（"有音频了"/"错误了"/"时钟到"）→  直接 SetBits(对应 bit)
   │                                                       ↓
   │                                                   事件组
   │                                                       ↓
   │                                              主循环 WaitBits 返回
   │                                                       ↓
   │                                                   if(bit&) 分派
   │                                                       ↓
   │                                                  执行固定逻辑
   │
   └─ 事情= 带 payload 的业务动作 → Schedule(lambda) → push_back 队列 + SetBits(SCHEDULE)
                                                            ↓
                                                      事件组
                                                            ↓
                                                      主循环 WaitBits 返回
                                                            ↓
                                                       if(bit& SCHEDULE)
                                                            ↓
                                                      从队列取 → 执行 lambda
```

**为什么要用三个：**
**原因 1：实时性与业务解耦。** 音频采样是硬实时（毫秒级），业务状态变更可以慢（几十毫秒）。混在一起会导致音频卡顿。所以分成不同任务、不同优先级。
**原因 2：多路等待。** 主循环要同时等"唤醒词 / 错误 / VAD / 时钟 / SCHEDULE / 音频发送"6 件事——EventGroup 一次等 6 路非常自然。而音频任务只等"音频包"一件事——Queue 更合适。
**原因 3：责任单一。** 如果所有事都塞给一个任务做（包括音频、网络），那个任务会被阻塞，整个系统死。**分工 + 优先级 = 让关键任务随时能抢占非关键任务。**
**核心一句话：不是"都用事件组"或"都用 Schedule"，而是"每个任务用最适合它的原语，让关键任务不被非关键任务拖累"。**

**什么用主循环，什么不用，为什么?** 
**用主循环（走 Schedule）：** 所有**应用层业务状态变更 + UI 更新**

| 什么用                  | 例子                               | 为什么            |
| -------------------- | -------------------------------- | -------------- |
| 改 `device_state_`    | `SetDeviceState(...)`            | 状态是共享的，单线程改最安全 |
| 刷屏幕                  | `display->SetChatMessage(...)`   | 显示驱动通常不是线程安全的  |
| 切 LED                | `led->OnStateChanged()`          | 共享硬件           |
| 发 MCP 回包             | `protocol_->SendMcpMessage(...)` | 保证顺序           |
| 需要"按顺序"的动作用 Schedule | "先连通道 → 再进入 Listening"           | 顺序敏感           |

**不用主循环（走自己的任务）：** 所有**实时性要求高 + 逻辑独立**

|什么不用|例子|为什么|
|---|---|---|
|音频采集/播放|I2S DMA|晚 1ms 就爆音，不能等主循环|
|唤醒词检测|AFE 引擎内部任务|高频信号处理|
|网络收发|LwIP / MQTT client|ESP-IDF 已经封装好任务|
|定时器回调|`esp_timer`|系统任务调度|
|看门狗|独立任务|必须在硬件层面守护|

**一句话：主循环负责"业务和状态"，专用任务负责"实时数据流"。**

**主事件循环为什么不能使用vTaskDelay?**
因为vTaskDelay对于CPU来说是非阻塞的，CPU同时可以去跑其他任务，但是对于调用者主事件循环来说是阻塞的，主事件循环里面的其他任务会因此阻塞。**主循环的设计目的：快速处理一个事件 → 立刻回到 WaitBits 等下个事件。**



#### 三、 为什么主循环里的事不能各自拆成"低优先级任务"？
**这个问题一针见血，直接踩在架构设计的核心决策上。答案是：可以拆，但拆了之后代价远大于收益。**

**拆成多个任务长什么样** 
假设拆掉主循环，改成 6 个独立任务：
```C
// 伪代码示意
TaskA("tts_handler",   优先级3); //：循环等 tts 消息，处理 TTS
TaskB("stt_handler",   优先级3); //：循环等 stt 消息，处理 STT
TaskC("wake_word",     优先级4); //：循环等唤醒词事件，处理唤醒
TaskD("clock",         优先级3); //：循环等时钟 tick，刷新状态栏
TaskE("vad_handler",   优先级3); //：循环等 VAD，刷新 LED
TaskF("error_handler", 优先级4); //：循环等错误，处理报错
```
看起来挺清晰，对吧？**但拆完之后，六个问题全部冒出来：**


**问题 1：状态竞争爆炸
**所有任务都要改同一个 `device_state_`：**
```C
// TTS 任务
if (device_state_ == Idle) device_state_ = Speaking;
// STT 任务（同时）
if (device_state_ == Idle) device_state_ = Listening;
```
**两个任务同时改 → 状态互相覆盖 → 系统错乱。** 这是最开始说的问题。

**解决办法：加锁。但加锁之后：**
```C
// TTS 任务
mutex_lock();
if (device_state_ == Idle) {
    device_state_ = Speaking;
    display->SetStatus("说话中");     // ← 慢操作，在锁里
    audio_service_.ResetDecoder();   // ← 又调别的锁，死锁风险
}
mutex_unlock();
```
**"在锁里调别的模块 = 死锁温床"。** 拆成 6 个任务 → 6 个任务全都要改共享状态 → 全都要加锁 → 锁的范围、顺序、嵌套全都要仔细设计 → 一不小心就死锁。**代码从 10 行变成 100 行，bug 概率高 10 倍。**


**问题 2：顺序不可控**
**状态切换是有顺序要求的：**
```text
Idle → Connecting → Listening → Speaking → Listening → Idle
```

**拆成任务后，多个任务"同时"想改状态：**
```text
TTS 任务：现在应该改 Speaking
网络任务：现在应该改 Connecting
```

**谁先谁后？** FreeRTOS 调度器说"看优先级、看时间片"，**但业务上的顺序是"先 Connecting 才 Listening"，跟调度器优先级没半毛钱关系**。

**要保证业务顺序，只能加锁 + 条件判断：**
```C
mutex_lock();
if (device_state_ == Connecting && channel_opened) {
    device_state_ = Listening;
}
mutex_unlock();
```
**这样代码里到处是"状态判断 + 加锁"，业务逻辑被淹没在并发控制里。** 这就是为什么单线程事件循环是经典架构——**它把"顺序"变成了"代码顺序"，不需要额外表达。**


**问题 3：内存爆炸**
**每个 FreeRTOS 任务都需要独立的栈**（一般 2-4KB，复杂任务 8KB+）。

**ESP32-S3 的 SRAM 总共 512KB，能用的大约 300KB 左右。** 拆成 6 个任务：
- 6 × 4KB = 24KB 的栈
- 每个任务的 TCB（任务控制块）约 200 字节
- 6 个任务 × 各种内部结构

**不算多，但"任务越拆越多"会累积。** 而且音频、网络已经各占几个任务了，再加 6 个业务任务，**内存压力上来，音频缓冲就小了，容易卡顿。**
**主循环方案：只 1 个任务，1 份栈，所有业务共用。** 内存省 5 倍。


**问题 4：调度开销**
**FreeRTOS 任务切换大约 1-5 微秒。** 看起来不多，但：
- 高频事件（比如每秒 30 帧 VAD 变化、每秒几十个音频包）
- 每来一个事件就要"唤醒任务 → 切换上下文 → 处理 → 再睡眠"
- 如果事件分散在 6 个任务里，**每个任务独立切换**，累计开销就上来了
**主循环方案：所有事件都投递到 1 个任务，任务切换次数少，调度器压力小。**


**问题 5：调试地狱** 
**单线程事件循环的 bug：** 打日志，看顺序，一眼能找到。
**6 任务并发的 bug：** 这次跑出错，下次跑不复现；打日志一看，顺序乱、时序乱、竞争乱。**多线程并发 bug 是嵌入式开发里最难查的一类。**

**问题 6：其实"低优先级"救不了你** 
你可能会想："都设低优先级，让它们慢慢跑不就好了吗？"

**但问题不是"优先级高低"，是"多个执行流并发改状态"。** 就算全是优先级 1，**调度器照样会每隔几毫秒切一下**，中间状态照样被破坏。

**低优先级只能保证"不抢占高优先级"，不能保证"不和同级任务竞争"。**


**主循环的"便宜"在哪儿？**
**主循环 = 用"架构设计"一劳永逸地消灭并发问题。代价是：**
- **主循环里不能阻塞**（要快速处理每个事件）→ 这是唯一约束
- **紧急事件必须能插队** → 用 bit 顺序实现
- **所有业务都得投递进来** → 用 Schedule 或 SetBits
**换来的收益：**
- **状态永远单线程改 → 不需要锁 → 不需要担心竞争**
- **顺序就是代码顺序 → 简单直接**
- **1 个任务 1 份栈 → 内存省**
- **所有业务在一处 → 调试简单**


**什么时候该拆成独立任务？** 
**只有当"实时性和业务逻辑"必须分离时，才拆。** 本项目拆的：

| 拆了    | 为什么                |
| ----- | ------------------ |
| 音频任务  | 硬实时（1ms 级），不能被业务耽误 |
| 网络任务  | 高延迟敏感，ESP-IDF 已封装  |
| 定时器任务 | 系统级，被 FreeRTOS 管   |

**剩下的业务逻辑全部塞进主循环。** 这是"实时流 → 独立任务；业务动作 → 主循环"的分界。


**一句话总结：**
> **主循环的方案 = "用一个线程 + 一个队列" 把并发问题从"到处加锁"降维成"一次性架构约定"。拆成多任务的方案 = "用 N 个线程 + N 把锁" 把代码复杂度从 1 变成 N²。工程上几乎必然选前者。**

### 1.2.2 任务优先级管理类
**是什么：** 它是一个 RAII（Resource Acquisition Is Initialization，资源获取即初始化）惯用法的工具类，用来在某个作用域内临时改变当前 FreeRTOS 任务的优先级，离开作用域时自动恢复。
**作用：** 任务的优先级不是固定的，需要根据当前的运行状态动态调整，需要任务优先级管理类来动态调整。
```C
/* 任务优先级重置 */
class TaskPriorityReset {
public:
    TaskPriorityReset(BaseType_t priority) {  //构造函数
        original_priority_ = uxTaskPriorityGet(NULL);   //记录初始优先级
        vTaskPrioritySet(NULL, priority);   //设置新的优先级
    }
    ~TaskPriorityReset() {   //析构函数
        vTaskPrioritySet(NULL, original_priority_);  //还原优先级
    }
private:
    BaseType_t original_priority_;
};
```
**核心价值：** 
1. **保护临界操作不被抢占：** 确保临界操作在执行过程中不被更高优先级的任务打断（通过提高任务优先级），保证操作的原子性
2. **自动恢复优先级，零遗漏：** 利用RAII机制，在对象销毁的时候自动恢复优先级，无需手动恢复，避免遗漏导致优先级混乱
3. **异常安全：** 即使函数中途抛出异常，析构函数也会被调用，确保优先级被正确恢复，不会遗留优先级混乱的bug
