# 1. 先看骨架
## 1.1 整体架构概览
```
xiaozhi-esp32/
├── main/                       ← ⭐ 全部业务代码（ESP-IDF 单"main"组件架构）
│   ├── boards/                 ← 板级支持（70+ 硬件适配层）
│   ├── audio/                  ← 音频子系统（编解码+唤醒词+处理链路）
│   ├── display/                ← 显示子系统（LVGL: LCD/OLED/表情）
│   ├── protocols/              ← 通信协议层（WebSocket / MQTT）
│   ├── led/                    ← LED 灯效控制
│   ├── assets/                 ← 多语言语音资源包（30+语言）
│   ├── application.cc          ← ★ 应用主控（状态机+事件循环）
│   ├── mcp_server.cc           ← MCP服务端（设备能力暴露）
│   ├── main.cc                 ← ★ 固件入口 app_main()
│   └── ...
├── partitions/                 ← 分区表（v2版本）
├── build/                      ← CMake构建缓存
├── docs/                       ← 文档与图片
└── CMakeLists.txt              ← ★ 顶层构建（选板型+组件配置）
```

| ★☆☆ | [ota.cc]                               | **OTA 升级**：固件下载→写入→重启                                 |

## 1.5 设计模式与架构特点

### 1.5.1 单例模式 + 工厂模式（Board）
```cpp
// board.h - 每个板型通过 DECLARE_BOARD 宏注册工厂函数
Board& board = Board::GetInstance(); // 内部调用 create_board() → new 具体板型

// CMakeLists.txt 根据 CONFIG_BOARD_TYPE_* 编译对应板型的 .cc 文件
// 每个板型的 create_board() 被链接器选中
```

### 1.5.2 策略模式（Protocol / AudioCodec / Display / WakeWord）

|基类|变体（策略）|
|---|---|
|`Protocol`|`WebsocketProtocol` / `MqttProtocol`|
|`AudioCodec`|`NoAudioCodec` / `BoxAudioCodec` / `Es8311Codec` / `Es8388Codec` …|
|`Display`|`LcdDisplay` / `OledDisplay` / `EmoteDisplay` / `NoDisplay`|
|`WakeWord`|`EspWakeWord` / `AfeWakeWord` / `CustomWakeWord`|
|`Board`|`WifiBoard` / `Ml307Board` / `DualNetworkBoard` + 70+ 具体板型|

### 1.5.3 事件驱动架构
```
esp_timer(1秒tick) ──▶ CLOCK_TICK ──┐
按键中断 ──▶ GPIO ISR  ──────────────┤
网络消息 ──▶ Protocol回调   ──────────┤──▶ Application::MainEventLoop()
唤醒词   ──▶ WakeWord回调   ─────────┤       ├── SetDeviceState()
VAD变化  ──▶ AudioService回调  ──────┘       ├── Schedule(callback)
                                            └── 更新 Display / LED
```

### 1.5.4 编译时多态（板型选择）

70+ 个板型，但**运行时只有一套代码**。通过 `sdkconfig` 中的 `CONFIG_BOARD_TYPE_*` 宏在编译阶段决定：

- 链接哪个板型的 `create_board()` 实现
- 选择哪套字体资源（不同屏幕尺寸用不同字号）
- 选择哪个 Emoji 表情集（大屏用 `twemoji_64`，小屏用 `twemoji_32`）

核心思路是：**一个 Application 主控 + 五层抽象策略（Board / Protocol / AudioCodec / Display / WakeWord）+ 编译时板型选择**，支撑了 70+ 种硬件的统一固件

## 2.4 核心机制总结（与 OV-Watch 的对比）

|维度|OV-Watch（STM32手表）|本项目（小智AI设备）|
|---|---|---|
|**编程语言**|C + FreeRTOS|**C++ + FreeRTOS**|
|**启动入口**|`main()` → HardwareInitTask|`app_main()` → `Application::Start()`|
|**任务模型**|13个 FreeRTOS 任务队列驱动|事件循环 + 状态机（1个 main_event_loop）|
|**核心调度**|多任务并行 + 消息队列|**事件标志组** (MAIN_EVENT_*) 推状态机|
|**UI 架构**|LVGL 页面栈管理|LVGL + 主题系统 + 表情/状态栏|
|**联网能力**|蓝牙 BLE|**Wi-Fi/4G + WebSocket/MQTT 云端**|
|**核心逻辑**|各类传感器采集展示|**AI 语音对话（唤醒词→听→说）**|
|**业务复杂度**|手表功能（计时/心率/指南针）|**云端 AI 交互 + 设备控制(MCP)**|

**一句话总结这个项目的整体运行逻辑**：
> 设备上电后，`app_main` 完成"底层存储 + 事件总线"初始化，然后 `Application::Start()` 一次性装配好 音频、网络、显示、升级 四套子系统，随后进入**"空闲"状态等待唤醒词**。平时由秒定时器刷新屏幕，一旦用户喊出"小智小智"，事件标志组触发 `MainEventLoop` 把状态机从 空闲→连接→听→说，走完"上行(录你的话)→云端AI→下行(播AI回话)"的完整语音闭环后，回到空闲。整个过程如同一个被**事件驱动的服务**，持续运行、随时响应。

### 阶段1：手工焊接原型（v0 面包板时代）

> **目标**：让一颗芯片能连上云端对话。**什么都没有，一切从零搭。**

```
┌───────────────────────────────────────────────────────────┐
│  硬件：一块 ESP32 开发板 + 面包板 + 飞线                    │
│                                                           │
│  ESP32 芯片                                                │
│   ├── I2S 引脚 → 外接 MEMS 麦克风（直接飞线焊）              │
│   ├── I2S 引脚 → 外接 MAX98357 功放 + 小喇叭                │
│   ├── I2C 引脚 → SSD1306 0.96寸 OLED（128x32/128x64）     │
│   ├── GPIO    → 外接 4 个轻触按键（BOOT/TOUCH/VOL+/VOL-）   │
│   └── GPIO    → 一颗 WS2812 RGB LED                        │
└───────────────────────────────────────────────────────────┘
```

**这一步写/移植的代码（按先后顺序）**：
```
1. 【ESP-IDF 最小工程】         从 esp-idf 模板拷贝 → 能编译烧录
2. 【WiFi 联网】               写 WiFi 连接逻辑 → 能从云端拉数据
3. 【WebSocket 协议】          写 WebSocket 客户端 → 能连上云端服务器
4. 【I2S 音频输入】            直接写 I2S 驱动读麦克风 → 有声音流
5. 【Opus 编解码】             集成 libopus → MIC→Opus→发送到云端
6. 【I2S 音频输出】            直接写 I2S 驱动写功放 → 能播放云端TTS
7. 【JSON 协议解析】            解析 cloud→device 的 JSON（tts/stt指令）
8. 【SSD1306 OLED 显示】       移植 SSD1306 I2C 驱动 → 显示文字
9. 【按键 GPIO 扫描】           写按键按下/双击/长按逻辑
10.【WS2812 LED 控制】         写单颗 RGB LED 灯效

此时项目的样子（bread-compact-wifi/config.h 是见证者）：
-------------------- config.h --------------------
#define AUDIO_I2S_MIC_GPIO_WS   GPIO_NUM_4       ← 手工焊接的引脚！
#define AUDIO_I2S_MIC_GPIO_SCK  GPIO_NUM_5
#define AUDIO_I2S_MIC_GPIO_DIN  GPIO_NUM_6
#define AUDIO_I2S_SPK_GPIO_DOUT GPIO_NUM_7
#define AUDIO_I2S_SPK_GPIO_BCLK GPIO_NUM_15
#define AUDIO_I2S_SPK_GPIO_LRCK GPIO_NUM_16

#define BUILTIN_LED_GPIO        GPIO_NUM_48
#define BOOT_BUTTON_GPIO        GPIO_NUM_0
#define TOUCH_BUTTON_GPIO       GPIO_NUM_47

#define DISPLAY_WIDTH   128
#define DISPLAY_HEIGHT  64              ← 小 OLED，够用就行
-------------------------------------------------
```

**这个阶段的代码特点**：没有抽象，所有硬件直写在 `main.cc` 里或一个大文件里。`no_audio_codec.cc`（直接 I2S，不用编解码芯片）是这个阶段的"遗产代码"，至今保留给无音频芯片的板型使用。

### 阶段2：抽象框架层——"我不想每块板都重写一遍"

> **动机**：手工焊的板子跑通了，但想换一块板子（比如换个显示屏、换颗编解码芯片）就要改一大堆代码。于是开始**抽基类**。

```
                    【先有实现，后抽抽象类】

    阶段1 的代码                       阶段2 重构后
 ┌──────────────────┐         ┌──────────────────────────┐
 │ main.cc 里啥都有   │         │ Board (抽象基类)           │
 │ ├ WIFI 连接逻辑   │   ──▶   │  ├─ WifiBoard             │
 │ ├ I2S 音频收发    │  重构    │  │   └─ CompactWifiBoard  │
 │ ├ OLED 驱动      │         │  └─ Ml307Board (4G)       │
 │ ├ 按键扫描       │         │                           │
 │ └ LED 控制       │         │ AudioCodec (抽象基类)      │
 └──────────────────┘         │  ├─ NoAudioCodec          │
                              │  └─ (以后加 ES8311等)     │
                              │                           │
                              │ Display (抽象基类)         │
                              │  ├─ OledDisplay           │
                              │  └─ (以后加 LcdDisplay)   │
                              │                           │
                              │ Protocol (抽象基类)         │
                              │  ├─ WebsocketProtocol      │
                              │  └─ MqttProtocol           │
                              └──────────────────────────┘
```

**这一步具体做的事情**：
```
1. 创建 Board 基类 (board.h/.cc)
   → 纯虚函数：GetAudioCodec() / GetDisplay() / StartNetwork() / GetLed()
   → 单例模式：Board::GetInstance()
   → 工厂模式：create_board() + DECLARE_BOARD 宏

2. 创建 WifiBoard 子类 (wifi_board.h/.cc)
   → 把 WiFi 连接逻辑从 main 搬到这

3. 创建 Ml307Board 子类 (ml307_board.h/.cc)
   → 抽象 4G Cat.1 联网逻辑

4. 创建 AudioCodec 抽象 (audio_codec.h/.cc)
   → 纯虚函数：Read() / Write() / Start() / Stop()

5. 创建 Display 抽象 (display.h/.cc)
   → 纯虚函数：SetStatus() / SetEmotion() / SetChatMessage()
   → OledDisplay 实现 → 搬入 SSD1306 代码

6. 创建 Protocol 抽象 (protocol.h/.cc)
   → 已有的 WebSocket 逻辑重构到 WebsocketProtocol

7. 创建 Application 主控制器 (application.h/.cc)
   → 状态机 + 事件循环 从 main 中抽出来
   → main.cc 只剩 30 行：初始化 NVS → app.Start()

8. 创建 CMakeLists.txt 构建体系
   → CONFIG_BOARD_TYPE_BREAD_COMPACT_WIFI 选择板型
   → 编译期决定 create_board() 链接哪个实现
```

**重构后的 main.cc（极其简洁）**：
```cpp
// 重构后：main.cc 只有 30 行，真正的逻辑全部在 Application 里
extern "C" void app_main(void) {
    esp_event_loop_create_default();    // 事件总线
    nvs_flash_init();                   // 存储
    Application::GetInstance().Start(); // 一行启动
}
```

```
     工序：
     ① 集成 ESP-SR 离线语音识别引擎（乐鑫官方库）
```

## 3.3 总结：作者的核心开发哲学
```

│              "先跑通再抽象，先抽象再扩散"                        │
│                                                             │

│                                                             │
```

```
│                                   │                                     │
│  ┌────────────────────────────────▼─────────────────────────────────┐  │
│  │  Application::MainEventLoop (事件循环)                            │  │
│  │                                                                  │  │
│  │  if (bits & MAIN_EVENT_SEND_AUDIO):                             │  │
│  │     while (packet = audio_service_.PopPacketFromSendQueue()):    │  │
│  │         protocol_->SendAudio(packet) ──────▶ WebSocket.binary() │  │
│  │                                                  │               │  │
│  │  ┌───────────────────────────────────────────────┘               │  │
│  │  │  WiFi / 4G ML307 网络栈                                      │  │
│  │  │  ───────────────────────────────────────────▶  云端 AI 服务   │  │

│  └──────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────────┘
```

## 4.3 最终总结：六流合一
把六条数据流放到一张图里，就是系统运行的全貌：
```
                        ┌──────────┐
                        │  云端AI   │
                        │ ASR+LLM+ │
                        │   TTS    │
                        └────┬─────┘
                  ②Opus下行 │  │ ①Opus上行
                ③JSON(tts)  │  │ ④JSON(mcp)
              ┌─────────────┼──┼──────────────┐
              │             │  │              │
              ▼             │  │              ▼
         ┌────────┐         │  │        ┌─────────┐
         │Display │         │  │        │MCP Server│
         │  LVGL  │         │  │        │  Tool   │
         └───┬────┘         │  │        └────┬────┘
             │              │  │             │
    ③屏幕刷新│              │  │      ④GPIO/PWM
             ▼              │  │             ▼
       ┌──────────┐    ┌────┴──┴─────┐  ┌──────────┐
       │  📺 LCD  │    │ AudioService │  │ 💡🔊☀   │
       └──────────┘    │  3个任务     │  │ 灯/音量/  │
                       │  +3个队列    │  │ 亮度     │
   ┌──────────┐       └──────┬───────┘  └──────────┘
   │ 🔘 按键  │────⑤─────────┘
   └──────────┘  ToggleChat
                 State()

   ┌──────────┐
   │ 🔴 LED  │◀───⑥ OnStateChanged ─── 状态机状态变化
   └──────────┘
```
**记住这三句话就够了：**
- **音频** = 两个 FreeRTOS 任务 + 三条队列 + Opus 编解码，构成"MIC→云端→SPK"的闭环管线
- **显示/MCP** = 云端 JSON 通过 `Schedule()` 投递到主线程，操作 LVGL 和 GPIO
- **按键/唤醒词/LED** = 硬件中断 → 回调 → 状态机 → 全链路联动
